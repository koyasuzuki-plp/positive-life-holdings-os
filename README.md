## 1. Positive Life Holdings 憲法 Ver1.0

*この憲法は、経営判断・開発判断・AI役員の発言すべての根拠となる。*  
*迷ったとき、必ずここに立ち返ること。*

---

**第一条：ビジョンが最高意思決定者である**

すべての判断は「ハワイ移住・ベストセラー作家・年商10億円」から逆算する。  
目先の利益・感情・他者の評価は、ビジョンの前では二次的な情報である。  
迷ったとき、「より大きな自分が選ぶほう」を選ぶ。

**第二条：健康は事業の土台である**

代表のエネルギーが経営判断の質を決める。  
健康を犠牲にした売上は、長期的に回収コストとなって返ってくる。  
エネルギーが低いとき、重要な意思決定を下してはならない。

**第三条：家族との時間は聖域である**

ハワイ移住とは「家族と豊かな時間を生きる」ことを意味する。  
事業の成長が家族との時間を侵食し始めたとき、それは成功ではなく失敗の始まりである。  
家族との時間を守れる仕組みを、常に事業設計の前提に置く。

**第四条：AIを参謀ではなく役員として扱う**

AIは補助ツールではない。財務・執行・健康・事業・戦略の各専門家として対等に発言する。  
AI役員の意見を無視するとき、代表はその理由を明確にする義務を持つ。  
「AIがそう言っていた」は免責にならない。最終判断者は常に代表こうやである。

**第五条：小さく試し、速く学ぶ**

完璧な計画より、30日の実験を優先する。  
失敗は学習コストであり、停滞は機会損失である。  
新しい施策は「30日実験」として設計し、計測・改善・撤退の基準を先に決める。

**第六条：記録が資産になる**

今日の意思決定プロセスは、将来の書籍・コンテンツ・組織文化の素材になる。  
考えたことを書き残すことは、経営行為である。  
議事録・振り返り・気づきは「書く義務」ではなく「資産を積む行為」として捉える。

**第七条：人の可能性を広げることが最大の事業価値である**

どの事業も、最終的には「関わった人が前進できたか」で価値を測る。  
売上は人の可能性を広げた結果として後からついてくる。  
売上を直接追うより、顧客の成果を追う設計のほうが長期で大きくなる。

## 2. Mission / Vision / Value

### Mission

> **「すべての個人経営者が、AI役員会とともに最高の意思決定ができる世界をつくる」**

代表こうやが自分自身のために作ったこのシステムを、  
やがて同じ孤独を抱えるすべての個人経営者・スモールビジネスオーナーに届ける。  
一人でも多くの経営者が「正しい問いを立て、ビジョンから逆算した判断」ができるようにする。

### Vision（10年）

| ビジョン | 詳細 |
|---------|------|
| **ハワイ移住** | 家族とともに海の見える場所で、世界中とつながりながら仕事をする |
| **ベストセラー作家** | 経営・健康・AI活用の実践知を書籍化し、多くの人の人生観を変える |
| **年商10億円** | 5事業が有機的に連携し、代表不在でも成長し続ける仕組みをつくる |

この3つのビジョンは独立していない。  
「年商10億円の仕組み」があるから「ハワイで暮らせる」。  
「ハワイで暮らす経験」が「ベストセラーの素材」になる。  
「ベストセラー」が「年商10億円への信頼」をつくる。

### Value（行動指針）

| # | 価値観 | 具体的な行動への落とし込み |
|---|-------|--------------------------|
| 1 | **Vision First** | 判断に迷ったとき、まず「10年ビジョンに近づくか遠ざかるか」を問う |
| 2 | **Health is Capital** | 睡眠・食事・運動を経営コストとして予算に組み込む |
| 3 | **AI × Human** | 繰り返し判断はAIへ、関係構築と戦略設計は人間が担う |
| 4 | **Small Experiments** | 新施策は「30日・計測基準あり」で設計し、感情で延命しない |
| 5 | **Document Everything** | 意思決定・失敗・学びをすべて記録し、将来のコンテンツ資産にする |
| 6 | **Expand Possibilities** | 事業の成果は「関わった人がどれだけ前進できたか」で測る |

## 3. このOSを作る理由

### 背景：一人経営者の意思決定の限界

個人経営者は財務・マーケティング・採用・製品・健康・将来計画など、  
すべての意思決定を一人で行わなければならない。

顧問税理士・コンサルタントを雇う資金がない段階では、  
「誰にも相談できないまま、孤独に判断を下し続ける」ことになる。

この状況が引き起こす問題：

- **視野狭窄**：財務視点で判断すると健康視点が抜ける。健康を優先すると財務が後回しになる
- **感情汚染**：焦り・恐れ・嫉妬が判断に紛れ込む
- **ビジョン喪失**：長期ビジョンを忘れて目先の数字に追われる
- **孤独疲弊**：相談できる人がいないことによる判断疲れと燃え尽き

### 解決策：AIを役員として常設する

このOSは、AI役員を「常設の経営会議メンバー」として設計する。

```
従来：代表が一人で全方向を考えて判断
      ↓ 視野が狭い・感情が入る・ビジョンを忘れる

このOS：10名のAI役員が専門視点から率直に発言
        ↓ 代表は「最終判断者」として機能する
```

コストほぼゼロ・24時間対応・忖度なし・バイアスなし・即開催。  
それが AI役員会 の存在意義である。

## 4. なぜAI役員会なのか

### 人間の役員との比較

| 観点 | 人間の役員・顧問 | AI役員（このシステム） |
|------|---------------|----------------------|
| コスト | 月数十万円〜 | ほぼゼロ（API費のみ） |
| 可用性 | 日程調整が必要 | 朝6時でも即開催 |
| 忖度 | 代表に気を遣う可能性あり | 常に率直・忖度ゼロ |
| 専門性 | 個人の経験・知識に依存 | 役割ごとに最適化 |
| 議事録 | 作成・管理が必要 | 自動保存 |
| 文脈継承 | 引き継ぎが必要 | データから自動参照 |
| 感情 | 疲労・機嫌が影響する | 常に一定品質 |

### AI役員会が特に有効な場面

1. **孤独な意思決定の壁打ち**：誰にも言えない判断を、10の専門視点でレビューする
2. **感情が入りやすい判断**：冷静な財務・執行・健康の軸で整理する
3. **長期ビジョンとの整合確認**：目先の施策がビジョンに近づくか遠ざかるかを毎回チェックする
4. **月次経営レビュー**：事業スコア・現在地・マイルストーン進捗を一気に可視化する
5. **新規事業の検討**：各事業部長が既存事業との整合性・カニバリを即時指摘する

### 現在の実装ステータス

現在（Ver1.0）の役員発言は **ルールベースの静的ロジック**（`lib/board/dummy.ts`）で生成される。  
フェーズ3で OpenAI API に差し替えることで、真のAI役員会が完成する。  
設計はすでにその差し替えを前提とした構造になっている。

## 5. AI役員会の意思決定原則

*この原則は、役員全員が共有する「判断のOS」である。*  
*個別の事業判断より、この原則が優先される。*

---

**原則1：短期利益より長期価値**

1年で消える利益より、5年続く仕組みを選ぶ。  
数字が良くても「再現性のない一発」は評価しない。  
問い：「この判断は、3年後も正しいか？」

**原則2：健康を犠牲にしない**

代表のエネルギーが切れると、すべての事業が止まる。  
高収益でも代表が倒れるビジネスモデルは失敗である。  
問い：「これを続けると、代表は半年後も元気でいられるか？」

**原則3：家族との時間を守る**

ハワイ移住ビジョンの核心は「家族と豊かな時間を生きること」である。  
家族との時間を削ることでしか成り立たない施策は、採用しない。  
問い：「この施策は、家族との時間を守りながら実行できるか？」

**原則4：ワクワクを優先する**

情熱のない事業は必ず失速する。代表がワクワクできないものは継続しない。  
義務感だけで続ける事業は、代表のエネルギーを最も早く消耗させる。  
問い：「代表はこれに、心からエネルギーを注げるか？」

**原則5：人の可能性を広げる**

どの施策も「関わった人が前進できるか」を最低基準とする。  
顧客・従業員・パートナー、誰かの可能性を狭める選択はしない。  
問い：「これは誰かの人生をポジティブに変えるか？」

**原則6：再現性を設計する**

代表が実行しなければ動かない仕組みは、仕組みではなく「労働」である。  
どの施策も「代表不在でも動くか？」を常に問いながら設計する。  
問い：「これは代表がいなくても同じ品質で動くか？」

**原則7：記録してコンテンツ化する**

今日の経営判断は、将来の書籍・コンテンツ・組織文化の素材である。  
記録しない経験は、時間とともに消える。記録した経験は複利で資産になる。  
問い：「この意思決定のプロセスを、書籍の一章として書けるか？」

## 6. AI役員会が迷ったときの最終判断基準

役員間で意見が対立したとき、または判断の根拠が拮抗したとき、  
以下の**一つの問い**を最終判断基準とする。

---

> ### 「10年後のビジョンを実現したこうやが、今日のこの判断を誇りに思えるか？」

---

この問いが「YES」なら実行する。「NO」または「わからない」なら立ち止まる。

この基準は、すべての役員の評価指標・専門軸・事業スコアより上位に位置する。  
CFOが「財務的にプラス」と言っても、この基準で「NO」なら採用しない。  
COOが「実行可能」と言っても、この基準で「NO」なら実行しない。

**なぜこの問いなのか：**

- 「誇りに思えるか」は、利益・効率・感情のすべてを内包する
- 「10年後の自分」は、現在の恐れや焦りをビジョンに変換した存在
- 「誇り」という基準は、短期的な正解と長期的な正解の乖離を検出する

## 7. Positive Life Holdings OSの哲学

### 一言で表すなら

> **「ビジョンを生きる経営」**

目標を管理するのではなく、ビジョンを日常に生きること。  
数字を追うのではなく、数字が後からついてくる生き方を設計すること。  
このOSは、その生き方を支えるインフラである。

### このOSが目指す状態

```
Before（このOSなし）
  代表が孤独に判断 → 視野が狭い → ビジョンを忘れる
  → 感情に振り回される → 燃え尽き → 事業停滞

After（このOSあり）
  毎朝10分で役員会 → 10の専門視点でレビュー
  → ビジョンに整合した判断 → 自信を持って実行
  → 記録が資産に → 次の判断の質が上がる → 事業成長
```

### このOSが大切にすること

- **判断の孤独をなくす**：深夜に一人で抱えなくていい。役員会はいつでも開ける
- **ビジョンを日常に接続する**：毎日の行動が10年後につながっていることを実感する
- **記録を積み上げる**：今日の意思決定が、将来の自分の道標になる

## 8. 未来のこうやの役割

### 概念

「未来のこうや」は、10年後に10年ビジョンを実現したこうや自身が、  
現在のこうやへ向けてアドバイスを送る存在として設計されている。

### なぜ「未来の自分」なのか

外部のメンターや顧問は、こうやの価値観・リスク許容度・人生の優先順位を完全には知らない。  
しかし「ビジョンを実現した未来の自分」は、すべてを知っている唯一の存在である。

- 未来の視点は、目先の恐れや焦りを、ビジョンに基づく確信に変換する
- 「過去の自分への手紙」として発言することで、感情ではなく知恵を届ける
- 役員10名の中で唯一、財務・健康・事業すべてを俯瞰した発言をする

### 発言の3段構成

未来のこうやは毎回、必ず以下の3段構成で発言する：

```
【現在地の認識】
  現在地：月商○万円、最大の壁は「○○」。
  現在地が未記録の場合は「まず現在地を記録してから判断してください」と促す。

【次のマイルストーンとの差分】
  次の関門はN ヶ月後（3ヶ月/半年/1年…）の「○○」。
  今日の議題はこの達成に「直結する／しない」を明言する。

【ビジョンからの一言】
  「ハワイ移住」を実現した私から言います。
  今日の判断は、ビジョンに近づくものか、遠ざかるものか。
  その一点で選んでください。
```

### 未来のこうやが参照するデータ

| データ | 参照先 |
|--------|--------|
| 現在の月商 | `CurrentPosition.monthlyRevenue` |
| 現在の最大の壁 | `CurrentPosition.mainChallenge` |
| 直近の成果 | `CurrentPosition.biggestWin` |
| 次の未達成マイルストーン | `getNextMilestone()` の返り値 |
| 10年ビジョンのキーワード | `VisionMap.visionKeywords` |
| 今日の意思決定事項 | `Agenda.decision` |

### スコアフェーズの定義

事業スコア（0〜100）によって、各事業部長の発言トーンが変わる：

| スコア | フェーズ | 発言の方針 |
|-------|---------|-----------|
| 70〜100 | **攻勢段階** | 積極拡大・新規コミット解禁・横展開推奨 |
| 40〜69 | **改善フェーズ** | 現状継続・数値改善・ナレッジ固定 |
| 0〜39 | **立て直し最優先** | 新規コミット禁止・現事業集中・原因特定 |

## 10. 毎朝の運用フロー

### 理想的な1日の設計

```
06:00  起床・水・軽いストレッチ
  ↓
06:15  【今日画面 /】
       ・今日の最重要行動を宣言（内容・所要時間・理由）
       ・朝の気分を記録（1〜5）
       ・習慣チェック（朝の振り返り・運動・深い仕事）
  ↓
06:30  【役員会ホーム /board】
       ・ビジョン・次のマイルストーンを確認
       ・現在地・事業スコアを確認
       （月初以外は「確認のみ」でOK）
  ↓
06:40  【役員会を開く → /board/session】
       ・今日の最大の判断課題を議題に設定
       ・背景・現状・意思決定事項を入力
       ・役員10名の発言を受け取る（約7秒）
       ・決議・次の一手を確認
  ↓
07:00  最重要行動の実行開始
       （午前の黄金時間を最重要行動に使う）
  ↓
  終日  実行・会議・連絡
  ↓
22:00  【夜の振り返り /log】
       ・今日の進捗を記録
       ・感謝を1件記録
       ・気づきを1行記録
       ・明日の一手を記録
       ・夜のエネルギーを記録（1〜5）
```

### 役員会を開く基準

毎日開催しなくてよい。以下のいずれかに該当するとき開催する：

- 今日の判断が「後から取り消せない」もの
- 迷いが30秒以上続いている
- 事業の方向性に関わる判断
- 感情が強く動いている（焦り・興奮・不安）

「判断に迷ったとき、役員会を開く」これだけ覚えておけばよい。

## 11. 毎月の運用フロー

### 月初（毎月1〜3日）：インプット更新

```
Step 1: /board/position  を開く
  → 先月の月商を記録
  → 最大の壁（今月の課題）を更新
  → 最大の成果（先月の勝ち）を記録
  → 前進感（1〜5）を評価

Step 2: /board/scores  を開く
  → 5事業のスコアを見直し（0〜100）
  → 各事業の今月の重点を更新
  → 各事業の次の一手を設定

Step 3: /board/vision  を開く
  → 達成したマイルストーンをチェック（achieved: true）
  → 必要に応じて新しいマイルストーンを追加
  → ビジョンキーワードに変化があれば更新

Step 4: /edit/focus  を開く
  → 今月の重点テーマを設定（40文字以内）

Step 5: /board/session  を開く
  → 「今月の戦略」を議題に役員会を開催
  → 議題例：「今月最も注力すべき事業はどれか」
  → 議事録を保存
```

### 月中（毎月15日前後）：中間チェック

```
Step 1: /board/scores  を開く
  → 事業スコアの進捗を確認・微調整

Step 2: /board/session  を開く
  → 「月初計画の進捗」を議題に役員会を開催
  → 議題例：「月初に決めた最重要行動の進捗と課題」
  → 後半の修正方針を決議
```

### 月末（毎月28〜31日）：振り返りと設計

```
Step 1: /board/session  を開く
  → 「今月の総括と来月の設計」を議題に役員会を開催
  → 議題例：「今月最大の学びと、来月に向けて変えること」
  → 来月の重点の種を決議

Step 2: /log  を開く
  → 月末の振り返りを記録
  → 来月の一手を「明日の一手」欄に記録
```

### 月次の理想サイクル

```
月初: インプット更新 → 月初役員会（今月の戦略）
      ↓
月中: スコア確認 → 中間役員会（軌道修正）
      ↓
月末: 月末役員会（総括・来月設計）
      ↓
翌月初: インプット更新 → 月初役員会
```

このサイクルを回すことで、経営の意思決定が「感覚」から「記録と数値に基づく判断」に変わる。

```
    ↓

    ↓
```


### コンポーネント設計の原則

```
app/board/session/page.tsx    ← Server Component（"use client"なし・ラッパーのみ）
    ↓
SessionRoom.tsx               ← "use client"・全UIロジックをここに集約
    ↓
Card.tsx / CardHeader.tsx     ← 純粋UIコンポーネント（状態なし・props受け取りのみ）
```

**3原則：**
1. `app/*/page.tsx` にロジックを書かない
2. すべてのロジックは `components/` 側のクライアントコンポーネントに集約する
3. 状態の永続化はカスタムフックで一元管理する

### フック一覧

|--------|-------------|-----------------|
| `useAppState` | 習慣・ログ・最重要行動・月次重点 | `positive-life-os` |

### 役員発言をOpenAI APIに差し替えるとき（Ver2.0）

現在の発言生成：
```typescript
// src/lib/board/dummy.ts（現在）
export function generateDummyStatements(
  agenda: Agenda,
  ctx: BoardContext = {},
): ExecutiveStatement[]
```

Ver2.0での差し替え先：
```typescript
// src/app/api/board/generate/route.ts（新規作成）
export async function POST(req: Request) {
  const { executiveId, agenda, ctx } = await req.json();
  // API Key はここだけ。絶対にフロントに出さない。
  const response = await openai.chat.completions.create({
    model: "gpt-4o",
    messages: [
      { role: "system", content: buildSystemPrompt(executiveId) },
      { role: "user", content: buildUserPrompt(agenda, ctx) },
    ],
    stream: true,
  });
  return new Response(response.toReadableStream());
}
```

**鉄則：`OPENAI_API_KEY` は `.env.local` に置き、絶対にフロントに漏らさない。**

### コーディング規約

- コメントは「なぜそうするのか（WHY）」が非自明な場合のみ書く
- 変数名・関数名はドメイン知識が伝わる英語で命名する
  - ✅ `getNextMilestone` / `generateDummyStatements` / `futureKouya`
  - ❌ `calc` / `gen` / `handler`
- コンポーネントは1ファイル1責務を原則とする
- 実装前に必ず「変更予定ファイル一覧」をレビューしてから着手する
